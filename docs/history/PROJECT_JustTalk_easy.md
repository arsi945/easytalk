# JustTalk easy (easytalk)

## Актуализация 2026-10-05 — приоритет над прежними планами платформ

Автор подтвердил: главный желаемый сценарий — полноценное личное использование
на iPhone; также нужны приложения macOS и Windows, Android позже. Для iPhone
пробуем собственную системную клавиатуру с обычным вводом, сначала как
дополнительную, в перспективе — для повседневного набора. Форк Telegram сейчас
не является обязательным путём реализации.

Актуальный сценарий и дополнение контракта `analyze_translate` описаны в
`JustTalk_easy_Input_Concept.md`: обычное поле → перевод на русский → необязательная
«Учёба» с объяснениями и словарём. Это решение автора имеет приоритет над прежним
composer/режимом тренировки. iPhone использует личный ключ OpenAI напрямую;
сервер — необязательный вариант. iOS-приложение и клавиатура успешно собраны,
подписаны и запускались на iPhone 12 Pro Max / iOS 27.0 через Xcode 16.2 на macOS 14.8.7.
Подробности и инструкция: `ios/README.md`.

## 1. Идея

Приложение для изучения иностранного языка через реальную ежедневную
коммуникацию.

Основной принцип:

> Пользователь пишет то, что ему реально нужно написать, сначала на
> изучаемом языке. Приложение исправляет ошибки, объясняет их и при
> необходимости переводит итоговый текст на родной язык для отправки
> собеседнику.

Пример:

Родной язык: русский.\
Изучаемый язык: английский.

Пользователь хочет сказать:

> Не знаю, будет ли у меня завтра время.

Пытается написать:

> I don't know will I have time tomorrow.

Приложение исправляет:

> I don't know if I'll have time tomorrow.

После изучения исправлений пользователь может получить естественный
русский вариант и отправить его собеседнику.

Цель: обучение происходит во время реального использования языка, а не
на искусственных учебных предложениях.

``` text
        ↓
Вставка текста в исходное приложение
```

## 3. Desktop MVP 0.1

Первая версия --- desktop-приложение.

На первом этапе не интегрироваться напрямую во все поля ввода ОС.
Использовать отдельное небольшое popup-окно.

### Сценарий

1.  Пользователь находится в Telegram, браузере, почте, редакторе и т.д.
2.  Курсор находится в поле ввода.
3.  Пользователь нажимает глобальную горячую клавишу.
4.  Открывается окно JustTalk easy.
5.  Пользователь пишет текст на изучаемом языке.
6.  AI анализирует текст.
7.  Приложение показывает:
    -   исходный текст;
    -   исправленный текст;
    -   ошибки;
    -   короткие объяснения.
8.  Пользователь может самостоятельно изменить текст.
9.  Пользователь запрашивает перевод на родной язык.
10. Приложение получает естественный перевод.
11. Результат вставляется обратно в приложение, из которого был вызван
    JustTalk easy.

## 4. Типы исправлений

AI должен различать типы изменений.

### Error

Реальная грамматическая ошибка.

``` text
He don't know.
→
He doesn't know.
```

### Unnatural

Неестественная формулировка.

``` text
I very like it.
→
I really like it.
```

### Style

Не ошибка, а альтернативный вариант.

``` text
I want to know your opinion.
→
I'd like to know what you think.
```

Изменения типа `Style` не должны навязываться.

Главная задача --- научить пользователя правильно выражать собственные
мысли, а не переписывать всё в AI-стиле.

------------------------------------------------------------------------

## 5. Уровни помощи

Приложение не должно всегда сразу показывать правильный ответ.

### Level 1 --- Direct correction

AI сразу показывает исправление.

### Level 2 --- Hint

AI сообщает тип ошибки и предлагает исправить её самостоятельно.

### Level 3 --- Highlight only

Приложение только показывает место ошибки.

### Цель

``` text
AI исправляет
    ↓
AI подсказывает
    ↓
AI только указывает ошибку
    ↓
Пользователь пишет самостоятельно
```

## 6. История обучения

Минимальная запись:



``` text

Topic:

```

## 13. Неизвестные слова

Если пользователь не знает нужного слова на изучаемом языке, он пишет
его на родном языке прямо внутри предложения.

Пример:

``` text
I need to купить some food before work.
```

Приложение определяет вставку:

``` text
купить
```

и предлагает:

``` text
I need to buy some food before work.
```

`купить → buy` автоматически добавляется в персональный словарь для
изучения.

Неизвестное слово --- отдельный тип события:

``` text
unknown_word
```

Пример данных:

``` json
{
  "source_word": "купить",
  "target_word": "buy",
  "source_language": "ru",
  "target_language": "en",
  "original_context": "I need to купить some food before work.",
  "corrected_context": "I need to buy some food before work.",
  "created_at": "...",
  "status": "new"
}
```

Отдельный модуль приложения.

Он содержит слова и выражения, которые пользователь реально не знал во

1.  Слово на родном языке внутри иностранного предложения.
2.  Явное добавление пользователем.

Для персонального словаря нужен отдельный механизм изучения.

Не ограничиваться стандартными карточками:

``` text

↓

```

Цель:

``` text

→

→

→

```

Метод изучения Vocabulary пока не фиксировать.

У пользователя есть собственные идеи по механике. Их необходимо
рассмотреть отдельно перед проектированием этого модуля.

``` text
        ↓

        ↓
```

Ключевой принцип:

> Пользователь в первую очередь изучает слова и выражения, которые ему

Пока не реализовывать:

-   мобильное приложение;

## 19. Критерии MVP 0.1

MVP считается рабочим, если пользователь может:

1.  Нажать глобальную горячую клавишу.
2.  Получить popup.
3.  Написать текст на изучаемом языке.
4.  Использовать родное слово внутри иностранного предложения, если не
    знает перевода.
5.  Отправить текст на AI-анализ.
6.  Увидеть исправленный вариант.
7.  Увидеть конкретные ошибки.
8.  Получить короткое объяснение ошибок.
9.  Получить перевод итогового текста на родной язык.
10. Вставить результат обратно в исходное приложение.
11. Сохранить историю взаимодействия.
12. Автоматически добавить неизвестные слова/выражения в Vocabulary.

## A1. Основной сценарий выбран неверно

**Проблема**

В §1 и §3 цикл завершается переводом на родной язык и отправкой
собеседнику. Значит, собеседник владеет родным языком пользователя, а
написание текста на изучаемом языке --- дополнительный шаг, не нужный для
самого сообщения.

Фактически есть два разных сценария:

``` text
Mode A — собеседник иностранец.
         Текст на изучаемом языке и есть результат.
         Приложение не добавляет лишних шагов.

Mode B — собеседник говорит на родном языке.
         Текст на изучаемом языке — только упражнение.
         Приложение добавляет шаг, не нужный для задачи.
```

Mode B держится исключительно на мотивации пользователя. При спешке
приложение будет пропущено. Документ ставит в центр Mode B.

**Решение**

-   Mode A --- основной сценарий, MVP проектируется под него.
-   Mode B --- отдельный режим `training`, включается явно.
-   Перевод на родной язык --- не часть основного цикла, а функция режима
    `training` и ручной вызов.

Основной цикл (Mode A):

``` text
Мысль пользователя
        ↓
Попытка написать на изучаемом языке
        ↓
AI-анализ
        ↓
Исправления + типы ошибок
        ↓
Финальный текст на изучаемом языке
        ↓
Вставка в исходное приложение
```

Перевода на родной язык в основном цикле нет.

## A2. Нет критерия качества исправлений

**Проблема**

§10 задаёт функции AI, но не задаёт способ проверки результата. Без
измеримого критерия изменение промпта или модели неотличимо от регресса.

**Решение**

Golden-set --- фиксированный набор тестовых предложений, минимум 100
записей, источник --- реальные ошибки русскоязычных в английском.

Формат записи:

``` json
{
  "id": "ru-en-0042",
  "text": "I think he didn't understood me.",
  "expect": [
    {
      "type": "error",
      "original": "didn't understood",
      "corrected": "didn't understand"
    }
  ]
}
```

Записи с `"expect": []` --- заведомо корректные предложения, правок на них
быть не должно. Их доля в наборе не ниже 20%.

Метрики:

``` text
precision        доля правок, соответствующих ожидаемым   ≥ 0.95
recall           доля найденных ожидаемых ошибок          ≥ 0.90
false_positive   доля правок на корректных предложениях   ≤ 0.05
type_accuracy    доля верно определённых типов            ≥ 0.85
```

`precision` и `false_positive` приоритетнее `recall`: ложная правка
дезориентирует изучающего сильнее, чем пропущенная ошибка.

Прогон набора обязателен перед любым изменением промпта или модели.
Golden-set создаётся до UI.

## A3. Over-correction

**Проблема**

Границы `error` / `unnatural` / `style` в §4 заданы примерами, но не
правилами. Модель по умолчанию переписывает текст под собственный стиль и
маркирует стилистические предпочтения как ошибки.

**Решение**

-   Ограничение minimal edit в промпте: менять только то, что нельзя
    оставить.
-   Запрет на замену лексики, если исходное слово корректно в контексте.
-   Каждая правка обязана иметь тип; правка без типа отбрасывается
    клиентом.
-   `style` по умолчанию скрыт, раскрывается по запросу.
-   Пользователь может отклонить правку. Отклонение сохраняется как
    событие:

``` text
correction_rejected
    diff_type
    original_fragment
    corrected_fragment
    grammar_topic
    timestamp
```

Повторно отклоняемые шаблоны правок понижаются в приоритете показа.

## A4. Латентность

**Проблема**

Popup вызывается в момент, когда пользователь пишет сообщение. Один
синхронный вызов, возвращающий исправление, типы, объяснения и темы, даёт
задержку, при которой приложение начнут обходить.

**Решение**

Разделить на независимые вызовы.

``` text
Pass 1  correct    исправленный текст + диффы с типами
                   быстрая модель, streaming
                   цель: < 1.5 с до первого токена

Pass 2  explain    объяснение + grammar_topic по одной ошибке
                   вызывается лениво, по клику на ошибку
                   результат кэшируется
```

`translate` и подбор неизвестного слова --- отдельные вызовы, не входят в
Pass 1.

------------------------------------------------------------------------

## A5. Стоимость запросов

**Проблема**

Каждое сообщение --- вызов модели. Не зафиксировано, на чём считается
экономика подписки.

**Решение**

``` text
Pass 1 correct     дешёвая быстрая модель   основная доля трафика
Pass 2 explain     сильная модель           редко, по клику
unknown_word       сильная модель           редко
translate          средняя модель           только Mode B / ручной вызов
```

-   Кэш объяснений по ключу `grammar_topic + нормализованный дифф`:
    одинаковая ошибка объясняется один раз.
-   Учёт токенов на пользователя --- с первой версии. Без него модель
    подписки не построить.

## A6. Приватность

**Проблема**

Приложение обрабатывает личную переписку и отправляет её внешнему API.
Позиция по данным в документе отсутствует.

**Решение**

Зафиксировать и показать в интерфейсе:

-   История хранится локально. Серверного хранения текстов в MVP нет.
-   Во внешний API уходит только текст текущего запроса.
-   Кнопка «не сохранять этот запрос» в popup.
-   AI Core обращается к провайдеру модели через интерфейс. Прямых
    вызовов конкретного API в Learning Core нет --- это условие для замены
    модели и для локальной модели в будущем.

## A7. macOS: разрешения и поставка

**Проблема**

§3 требует глобального хоткея и вставки в чужое приложение. Технические
последствия не зафиксированы.

**Решение**

Механика вставки:

``` text
сохранить текущий буфер обмена
        ↓
положить результат в буфер
        ↓
синтетический ⌘V
        ↓
восстановить прежний буфер
```

-   Требуется разрешение Accessibility --- отдельный экран onboarding с
    проверкой статуса и инструкцией.
-   Mac App Store не рассматривается: глобальный хоткей и Accessibility в
    песочнице нереализуемы. Поставка прямая, с подписью и нотаризацией.
-   Fallback без разрешения: результат остаётся в буфере обмена,
    пользователь вставляет сам. Основной сценарий обязан работать и в
    этом виде.

## A8. Механика смешанного ввода недооценена

**Проблема**

Фактически это главное отличие от существующих корректоров (Grammarly,
LanguageTool) и единственный честный источник Vocabulary --- слова,
которых пользователю реально не хватило.

**Решение**

Механика --- часть основного цикла, не дополнение. Подстановка входит в
Pass 1 и в MVP 0.1 как тип диффа `unknown_word`. Модуль Vocabulary
(хранение, список, изучение) --- 0.2, сама подстановка от него не зависит.

## A10. Уровни помощи как глобальная настройка

**Проблема**

§5 описывает уровни 1/2/3 как режим приложения. Пользователь уверенно
владеет одними темами и путается в других; единый уровень для всех

## A12. Контракты AI Core

Дополнение 2026-10-05: `analyze_translate`, schema_version 1, описано в
`JustTalk_easy_Input_Concept.md`. Прежние `correct`/`translate` совместимы.

**Проблема**

§10 задаёт функции прозой. Разработка ведётся через LLM (§20), для
которой проза --- ненадёжный контракт.

**Решение**

Зафиксировать ввод/вывод. Ниже --- минимальный набор для 0.1. При
расхождении реализации и этого раздела правится документ, а не молча код.

### correct

Request:

``` json
{
  "op": "correct",
  "schema_version": 1,
  "text": "I need to купить some food before work",
  "native_language": "ru",
  "target_language": "en",
  "context": "casual_chat"
}
```

Response:

``` json
{
  "schema_version": 1,
  "corrected": "I need to buy some food before work.",
  "diffs": [
    {
      "id": "d1",
      "type": "unknown_word",
      "original": "купить",
      "corrected": "buy",
      "start": 10,
      "end": 16
    }
  ]
}
```

``` text
type     error | unnatural | style | unknown_word
start    смещение в code points исходного текста
end      смещение в code points исходного текста
```

Пустой `diffs` --- корректный ответ, означает отсутствие правок.

### explain

Request:

``` json
{
  "op": "explain",
  "schema_version": 1,
  "sentence": "I think he didn't understood me.",
  "original": "didn't understood",
  "corrected": "didn't understand",
  "native_language": "ru",
  "target_language": "en"
}
```

Response:

``` json
{
  "schema_version": 1,
  "grammar_topic": "Past Simple / auxiliary verb",
  "explanation": "После didn't используется базовая форма глагола.",
  "explanation_language": "ru"
}
```

`grammar_topic` --- из закрытого списка категорий §7. Список расширяется
только правкой этого документа.

### translate

Request:

``` json
{
  "op": "translate",
  "schema_version": 1,
  "text": "I need to buy some food before work.",
  "from": "en",
  "to": "ru",
  "context": "casual_chat"
}
```

Response:

``` json
{
  "schema_version": 1,
  "translated": "Мне нужно купить еды перед работой."
}
```

## B1. Официальный клиент не является целевой платформой

**Проблема**

Официальные мобильные клиенты Telegram не имеют API расширений.
Встроиться в поле ввода невозможно. Доступные механизмы и их
ограничения:

``` text
inline-режим бота
    работает в любом чате
    нельзя отредактировать текст перед отправкой → уровни помощи 2-3
      из §5 недоступны
    запрос приходит на каждую паузу набора → стоимость
    ограниченное время на ответ → Pass 2 из A4 не проходит
    метка «via @bot» у отправленного сообщения, убрать нельзя
    нет места под разбор ошибок

бот в личном чате
    полный UI
    нет отправки в целевой чат, только copy-paste

Mini App, запуск из inline-режима
    полный UI, правка текста, Pass 2 без дедлайна
    отправка только через switchInlineQuery → снова inline-результат
      и метка «via @bot»
    вход в два шага

Mini App, запуск из attachment-меню
    недоступно: только для крупных рекламодателей Telegram Ad Platform,
    всем ботам — лишь на тестовом сервере

собственная клавиатура
    работает во всех приложениях
    iOS требует Allow Full Access для сети, лимиты памяти расширений
    Android показывает системное предупреждение
    придётся делать полноценную клавиатуру, иначе её не оставят основной
```

API для записи в поле ввода чата не существует. Любая отправка внутри
Telegram идёт через inline-результат, поэтому метка «via @bot»
неустранима на всех вариантах, кроме ручной вставки из буфера.

**Решение**

Официальный клиент используется только как тестовый стенд: бот в личном
чате для проверки качества исправлений (A2). Продуктом бот не является.

## B2. Форк клиента --- целевая платформа

**Проблема**

Все ограничения B1 происходят из одного факта: приложение не владеет
полем ввода.

**Решение**

Интеграция в собственный форк клиента Telegram. Форк владеет композером,
поэтому исходный сценарий §3 реализуется нативно:

``` text
пользователь пишет в композере на изучаемом языке
        ↓
ошибки подчёркиваются на месте, как у спеллчекера
        ↓
тап по подчёркиванию → объяснение
        ↓
правка в том же поле
        ↓
обычная отправка
```

Снимается:

``` text
метка «via @bot»                неустранимая в B1
лишние шаги входа               popup/Mini App не нужны
дедлайн inline-ответа           Pass 2 вызывается свободно
стоимость на нажатие клавиши    дебаунс локальный
уровни помощи 2-3 из §5         правка идёт в самом поле ввода
одобрение Telegram              не требуется
разрешения ОС                   не требуются
```

## B3. Новая поверхность: входящие сообщения

**Проблема**

Все варианты из B1 и исходный документ работают только с исходящим
текстом. Входящие сообщения --- бесплатный поток реального учебного
материала --- не используются.

**Решение**

В форке доступно действие на сообщении собеседника:

``` text
тап по входящему сообщению
        ↓
разбор конструкции / перевод фрагмента
        ↓
незнакомое слово или выражение → VocabularyItem
```

Vocabulary из §14 получает второй честный источник, помимо механики §13:
слова, встреченные в реальной переписке, а не только те, которых не
хватило при письме.

## B5. GPL и размещение логики

**Проблема**

Официальные клиенты Telegram распространяются под GPL, форк наследует
лицензию. Логика обучения, слинкованная в клиент, подпадает под
требование открытия исходников. Конкретную версию лицензии проверить в
репозитории форка.

**Решение**

Границу провести по процессу, а не по модулю:

``` text
сервер   AI Core, промпты, классификация ошибок, golden-set
         HTTP API
клиент   UI, локальное хранилище, дебаунс, подчёркивание
```

Побочные следствия, полезные независимо от лицензии:

-   одна реализация ядра на iOS и Android;
-   смена модели и правка промптов без релиза клиента;
-   учёт токенов на пользователя из A5 --- на сервере;
-   бот из B1 и будущий desktop-клиент используют то же API.

**Проблема**

## B7.1. Политика обновлений форка

**Проблема**

Влитие изменений upstream --- не разовая задача, а постоянная статья
расходов. Формально обновлять форк необязательно, поэтому нужно
зафиксировать, когда это допустимо.

Последствия отказа от влитий:

``` text
протокол       клиент объявляет серверу версию схемы API (layer).
               Telegram добавляет в схему новые типы контента; клиент
               на старом layer показывает «сообщение не поддерживается
               вашей версией». Старые layer'ы со временем отключаются,
               то есть в пределе клиент перестаёт работать
безопасность   исправления ошибок разбора данных и работы с шифрованием
               не доезжают до пользователей; для приложения личной
               переписки это основной риск
платформа      iOS и Android требуют сборки под свежие SDK и минимальные
               target API; upstream делает эту работу непрерывно,
               без влитий её делаете вы
функции        пользователи сравнивают с официальным клиентом; улучшения
               форка — добавка к Telegram, а не замена
накопление     пропущенные влития удорожают следующее; частые мелкие
               merge дешевле одного большого
```

**Решение**

``` text
0.1            форк не затрагивается
0.2            upstream заморожен на конкретной версии, влития не
               делаются. Цель этапа — проверить механику в реальной
               переписке на себе и нескольких тестерах
с появлением   влития обязательны, регулярно, по тегам upstream
пользователей
```

Правила изоляции кода, снижающие цену влитий:

``` text
код easytalk — в новых файлах, не правками внутри файлов upstream
точек вмешательства в код upstream — минимум, в идеале один вызов-хук
композер расширяется, не переписывается
изменения хранятся набором отдельных коммитов; rebase на теги upstream,
    не merge
логика на сервере (B5) — главный рычаг: чего нет в форке,
    то не конфликтует
```

Если расхождение форка с upstream уже глубокое («полностью переписан» в
буквальном смысле), влития дороги независимо от easytalk, и поддержка
клиента мессенджера становится крупнейшей статьёй расходов проекта ---
больше самой функции. Это требует подтверждения (B9).

``` text
      уровни помощи (§5, A10)

0.3   форк Telegram (B2), мобильная платформа

позже Windows (переносимость платформенного слоя), распространение
```

Мобильная платформа остаётся непокрытой до 0.3. Для личного
использования на desktop это принимается.

### Условия, сохраняющие путь к B2 и B5

``` text
промпты        внешние файлы данных, не строковые литералы в коде
golden-set     прогоняется отдельным скриптом, без запуска UI
границы        модуль AI Core принимает request JSON и возвращает
               response JSON по контрактам A12; позже заменяется
               HTTP-вызовом без правки вызывающего кода
```

Следствие: переносимый актив проекта --- промпты, golden-set и контракты,
то есть данные, а не код. Поэтому язык и стек UI на 0.1 выбираются по
скорости разработки, а не по переносимости. Требование переносимости
возвращается только на этапе Windows.

## C4. Платформа macOS: решения от 2026-10-01

### Gatekeeper

Gatekeeper проверяет не отсутствие подписи, а атрибут
`com.apple.quarantine`, который ставит скачавшая программа. Приложение,
собранное локально, этого атрибута не имеет, диалог «неизвестный
разработчик» не появляется. Он появится при передаче сборки скачиванием,
AirDrop или мессенджером. Снимается
`xattr -d com.apple.quarantine <app>` или System Settings → Privacy &
Security → Open Anyway. Начиная с macOS 15 быстрый путь через правый клик
→ Open убран.

### Accessibility и подпись

Для вставки в чужое приложение (A7) нужно разрешение Accessibility. TCC
привязывает его к подписи бинарника. У ad-hoc подписанного приложения
требование строится на хеше кода и меняется при каждой пересборке,
разрешение аннулируется.

``` text
подпись         Personal Team: вход в Xcode под обычным Apple ID,
                идентичность «Apple Development», бесплатно; программа
                за $99 нужна только для нотаризации и распространения
bundle id       фиксированный
путь установки  фиксированный, например /Applications/easytalk.app,
                а не каталог DerivedData
сброс           tccutil reset Accessibility <bundle-id>
fallback        результат остаётся в буфере обмена (A7); работает без
                Accessibility, приложением можно пользоваться до
                решения вопроса с подписью
```

## C5. Выбор стека 0.1: решение не принято

Сборка на macOS 14 снимает потолок Xcode 14.2, поэтому выбор --- обычный
компромисс.

``` text
                           AppKit (нативно)        Electron
подчёркивание в поле       NSTextView, механизм    contenteditable,
ввода                      есть, объёма больше     часы работы
popup, фокус, запуск       лучше                   требует возни
память в простое           десятки МБ              150-250 МБ
хоткей и ⌘V                напрямую                нативный модуль или
                                                   osascript
надёжность кода от LLM     ниже                    выше
```

Уточнения:

-   В SwiftUI нет полноценного редактирования форматированного текста,
    даже в SDK macOS 14. Для подчёркиваний нужен `NSTextView` через
    `NSViewRepresentable`.
-   Tauri использует системный WKWebView, на Monterey он старый
    (часть современного CSS/JS недоступна). Тот же потолок, что у
    нативного пути, только в другом месте.
-   Electron: приложение должно постоянно висеть в меню-баре, хоткей
    только показывает окно. Запуск процесса по хоткею слишком медленный.
-   Платформенный слой (хоткей, определение активного приложения,
    синтетический ⌘V) нужен в любом стеке. Webview добавляет прослойку,
    но от этой работы не избавляет.

Рекомендация ассистента: Electron --- надёжнее код от LLM, дешевле ключевой
элемент UI. Нативный путь лучше по качеству popup и памяти. Решение за
автором.

## C6. Перенос на Windows

Горячая клавиша, вставка и поставка переписываются под каждую ОС; UI и
ядро переносятся бесплатно только на webview-стеке.

``` text
горячая клавиша     macOS: RegisterEventHotKey / монитор NSEvent
                    Windows: RegisterHotKey (Win32)
вставка             macOS: буфер + ⌘V через CGEvent, Accessibility
                    Windows: буфер + SendInput Ctrl+V, отдельного
                    разрешения нет
активное окно       разные API (нужно для контекста §9)
автозапуск, трей    разные механизмы
поставка            macOS: подпись + нотаризация
                    Windows: сертификат подписи кода, иначе SmartScreen
краевые случаи      Windows: UAC --- из обычного процесса нельзя послать
                    ввод в окно с повышенными правами
```

Оценка: хоткей --- дни, надёжная вставка --- одна-две недели на ОС, время
уходит на краевые случаи. Разрешение Accessibility --- проблема только
macOS. Требование переносимости стека возвращается на этапе Windows
(после 0.3); на 0.1 стек выбирается по скорости разработки (B10).
