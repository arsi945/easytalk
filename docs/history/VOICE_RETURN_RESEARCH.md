# Диктовка из клавиатуры: повторное исследование, 8 октября 2026

**Результат: найден новый кандидат для автоматического перехода и возврата. Рабочего исправления на iPhone пока нет.** Телефон остаётся на 0.5.0/build20. В этом этапе приложение не менялось, не устанавливалось, микрофон не включался. Пользовательские фразы, аудио и ключи не использовались. Архив перед исследовательской документацией: `archive/20261008-045308-before-voice-return-research.tar.gz`.

## Что прояснилось

Последний отказ связан с запуском записи, а не с качеством распознавания: наш `Button(intent:)` выполнил действие внутри keyboard extension. В main app аудиодвижок не запустился. Это уже подтверждённый провал конкретного маршрута; повторять установку build20 и просить разрешения заново бессмысленно.

Успешная диктовка **внутри самого easytalk** ранее подтверждена. Реальный микрофон в фоне Notes/Telegram отдельно не подтверждён. Синтетический WAV и успешная компиляция эту проверку не заменяют.

Ручная подготовка микрофона каждые пять минут и переключение клавиатур автору не подходят. Короткий **автоматический** переход в easytalk с автоматическим возвратом — отдельный вариант. Он вынесен пользователю на уточнение, ответа в момент написания нет. Не считать молчание разрешением или заменять автоматический возврат инструкцией «вернись вручную».

## Готовый KeyboardKit: проверена совместимость, не только реклама

Исследован tag **10.9.7**, commit `fd7a231b58e1485b5226fc5b136bcd45d775fc21`. Получен официальный XCFramework; SHA256 ZIP совпал с Package.swift: `feb093c0e292c6db0f194c6fb869929d3ea5d4a7c7c4262e3d599b704194e7ae`.

Минимальный `import KeyboardKit` **не компилируется** нашим Xcode16.2/Swift6.0.3: модуль импортирует отсутствующий в SDK18.2 `FoundationModels`, его интерфейс создан Swift6.3.3. Лог: [evidence](evidence/voice-research/keyboardkit-import-xcode16.log). Инспектировались опубликованные Swift interfaces; бинарник не дизассемблировался и не исполнялся. Пробный доступ к Pro не активировался.

[Текущий тариф](https://keyboardkit.com/pricing) с Dictation и Host App Utils — Gold $500/месяц; есть пробный период. Это существенная зависимость, а не бесплатный компонент. Покупок/регистраций не было. Простого добавления SDK к нынешнему проекту недостаточно; обновление Xcode/macOS и совместимость Mac надо оценивать отдельно.

## Бесплатный кандидат: только определение приложения

Прочитан [KeyboardHostBundleID](https://github.com/Muskupecli/KeyboardHostBundleID/tree/f1106dd9f1f09e01c9c28e10e2882990bb14acdc), MIT, pinned commit `f1106dd9f1f09e01c9c28e10e2882990bb14acdc`. Заявлены Swift5.9/Xcode15+. Новый путь использует **private UIKit API и method swizzling**; это нельзя описывать как поддерживаемый Apple публичный API. На iOS26.4+ перехватываются сообщения keyboard arbiter, извлекается идентификатор host. В старом пути используется private host PID/XPC.

Код возвращает только свежий результат либо nil. Исторический cache нельзя использовать как адрес возврата: он может принадлежать предыдущему приложению. Сам пакет **не включает запись и не возвращает пользователя**. Его исходники прочитаны, но не добавлены в targets, не выполнялись и не проверялись на нашем iPhone. Заявления README о версиях iOS не заменяют такую проверку.

Для отдельного экспериментального прототипа это более компактный кандидат, чем миграция всей клавиатуры. Для выпуска в App Store остаются совместимость и использование private API. Действующее ограничение проекта на private selectors не отменено. Наличие MIT-лицензии решает право использования кода, но не правила Apple.

## Конкретная схема следующего прототипа

Если автоматический переход подходит, проверять сначала **Notes и Telegram**, затем расширять поддержку. Не обещать универсальный возврат только по bundle ID: идентификация приложения и его открытие — разные задачи. Публичный `openURL` открывает зарегистрированную схему; восстановление того же чата/заметки/фокуса нужно проверять отдельно. Не подставлять универсально private `LSApplicationWorkspace`/`suspend`.

1. Нажатие 🎙 фиксирует UUID документа, положение курсора, revision и одноразовый request. Текст поля остаётся в памяти клавиатуры; в launch URL его нет.
2. Для холодного запуска основное приложение получает команду на диктовку. Проверяет ticket/срок/разрешения и активирует настоящий AVAudioEngine. Обратный переход допускается после подтверждения готовности аудио, а не по произвольному таймеру.
3. Определённый и поддерживаемый host получает возврат. Неизвестный или устаревший host не открывается наугад. Процесс запуска ограничен по времени; при отказе запись выключается.
4. Вернувшаяся клавиатура продолжает исходный запрос. Распознавание остаётся локальным Apple Speech, окончание — после **3 секунд тишины**. На этапе перехода endpoint не должен завершать пустой запрос до того, как пользователь сможет заговорить.
5. Результат вставляется однократно только в подтверждённое исходное поле; смена документа/курсора/host запрещает автоматическую вставку. Потеря snapshot после перезапуска extension требует явной вставки, а не восстановления по текстовому совпадению.

### Что в нашем коде мешает даже после решения запуска

- `KeyboardViewController.viewWillDisappear` безусловно вызывает `cancelVoice()`. Плановый переход к recorder сейчас отменил бы свой же запрос. Нужна ограниченная по времени фаза перехода, а не глобальное отключение отмены при исчезновении.
- `fieldChanged` увеличивает revision при неизвестном nil/nil контексте. Переходные callbacks нужно отделить от реальной смены поля; защиту приватного/пустого поля сохранять.
- Неактивный controller не должен забрать результат у вернувшегося controller. Нужно явно разделить владение запросом, ожидание возврата и получение/подтверждение результата.
- `VoiceLaunch` валидирует ровно три параметра. Адрес возврата нельзя просто принять из произвольной строки; нужен ограниченный известный маршрут и защита от повторного запуска.
- Холодный `Button(intent:)` не заменять прямым `perform()`/`callAsFunction()` — это тоже локальное исполнение. SwiftUI Link может открыть app, но само по себе не решает возврат.

### Проверка, после которой можно говорить «работает»

На реальном iPhone, без открывания easytalk заранее: Notes → 🎙 → запуск и автоматический возврат → произнесённая фраза → 3s тишины → однократная вставка в тот же документ. Повторить в Telegram; отдельно проверить смену приложения/курсор/удаление поля во время записи, быстрые повторные taps, отказ разрешений, прерывание звонком, холодный процесс и окончание сессии. Нужны реальные audio/background/return события и пользовательский результат, не только тесты с WAV.

Metadata содержит только этапы/длительности/причины отказа, без текста, аудио и capability token. Установку делать поверх текущей, сохраняя Keychain/контейнеры/Team/IDs. App Groups не добавлять. До принятия UX и выбора допустимого навигационного механизма эту схему не выдавать за готовый фикс.
